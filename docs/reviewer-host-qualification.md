# Synthetic host-handoff qualification

The reusable reviewer has an opt-in `host_qualification` mode, default `false`, that produces a synthetic bundle and signs host-only handoff bytes in a fresh job. Normal callers retain their existing review behavior. Qualification excludes the sanitize, provider review, and execution-receipt jobs. It makes no SDK, provider, native-client, completed acquisition, or hosted-success claim. No caller or dispatch is installed by this change. The old templates under `scripts/fixtures/reviewer-host-qualification/` remain disabled historical review contracts; the actual source/seal implementation is in `.github/workflows/claude-pr-reviewer.yml`.

## Boundary

`captureQualificationPublication()` invokes the existing producer and captures its publication callback. Only the host returns the serialized attempt identity and envelope digest. A fresh sealing job accepts those two platform `needs` outputs plus independently captured platform context; it cannot obtain identity from downloaded producer JSON. The signer attests the resulting `reviewer-host-handoff.json` bytes using `actions/attest-build-provenance` v4.2.2 pinned to `4d101475d8b20a2381f78447822ac1eab6504dd8`.

A separate acquisition run starts after the source attempt finishes. `acquireQualificationEvidence()` verifies the handoff signature before parsing identity, checks authenticated run/attempt and job metadata, validates the existing producer bundle, invokes the existing composer, and checks the source metadata and bundle again before publishing without overwrite. Repository ID, caller source SHA, reusable workflow SHA, run ID and attempt are trusted host policy. A branch name alone does not prove protection. Artifact bytes, names and attestation predicate identity are not authority.

The acquisition API accepts a host-prepared directory and bounded handoff/bundle buffers. It does not download or extract archives. The authenticated GitHub `get` port and optional verifier port are trusted host dependencies; neither can be selected by artifact content. Tests inject a verifier stub explicitly. A production caller must use the default pinned cryptographic verifier.

## Source and sealing jobs

Qualification accepts only a manual dispatch from private `knitli/knitli-site` (repository ID `1058277548`), protected `main`, through `.github/workflows/reviewer-host-qualification.yml`. Both jobs reject unsupported context before checkout. They use raw `job.check_run_id`, `job.workflow_ref` and `job.workflow_sha`; branch refs are not normalized into immutable-looking refs. Missing or differently serialized platform fields fail closed. A future hosted run must establish their actual representation.

Both jobs check out only `knitli/.github` at the defining workflow SHA, using pinned checkout `9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0`, with no persisted credentials or submodules. Pinned setup-node `949feb2413d6458794dcd2491c4babbbce0c15c1` installs exact Node `24.21.0`. The host CLI requires that version, verifies checkout HEAD and a clean tree, then validates platform context independently. It never accepts a caller-selected script, source repository, output path or command. Jobs run on `ubuntu-24.04` with ten-minute timeouts; action pins do not make the mutable runner image an immutable runtime.

The producer has only Contents read permission. Its real fixture/producer callback supplies the only two platform outputs; child stdout is never parsed. Output serialization permits only the exact bounded schema, rejects multiline injection, and requires an empty regular platform output file. The three fixed producer files are each capped at 64 KiB and together at 128 KiB. The fresh sealer consumes only its internal producer `needs` outputs and independently captured context, never a downloaded producer artifact. Only that job has OIDC and Attestations write permission. Existing required provider-secret declarations remain unchanged; a separately reviewed caller must pass invalid unused placeholders, never inherited real credentials, for qualification.

The pinned provenance action signs `reviewer-host-handoff.json` by its exact SHA-256 and publishes an attestation to GitHub. Only after that step succeeds does the host retain its regular, nonsymlink `attestation.json` from inside the runner temporary directory, capped at 2 MiB, under a fixed artifact filename. The host rechecks the sealed identity/digest and refuses extra files or overwrite. This copy is transport, not cryptographic acquisition verification. Producer and sealer upload exactly three and two named files respectively, through pinned upload-artifact `ea165f8d65b6e75b540449e92b4886f43607fa02`, with one-day retention, no overwrite, no hidden files and no compression. Upload-artifact's internal Node20 runtime is separate from the pinned Node24 host CLI.

Local tests execute the real host CLI against temporary committed source and simulated platform environment, including actual fixture publication. Negative tests exercise both preflight scripts, exclude all legacy jobs in qualification mode, preserve default predicates, reject forged/raw-ref context, dirty source, unsafe output files and oversized attestation transport. These tests produce no genuine GitHub OIDC signature and do not establish a successful hosted run.

## Verified schema and pins

The local verifier is GitHub CLI **2.101.0**, revision `0cf1092493af067646fc5f3db9421c6a6ec9c938`, macOS arm64 executable SHA-256 `aa97dfb4a82f7c56063cdcbfaa39a738b923c1bdca29bd5a041b8e959ca38e04`. Its absolute executable path is intentionally local. Other platforms refuse verification. The checked-in GitHub trusted-root JSONL has SHA-256 `26b3382d5700afbcd84f980d1d5b6c52bff743dc2a8ee86b8b44c8e1245ce485`; it is the GitHub-only record acquired with the pinned CLI's `attestation trusted-root --hostname github.com` on 2026-10-17, not a fixture CA. Public Sigstore identities are denied. Root refresh is a reviewed code change.

Primary sources:

- [CLI policy](https://github.com/cli/cli/blob/0cf1092493af067646fc5f3db9421c6a6ec9c938/pkg/cmd/attestation/verify/policy.go) and [verification implementation](https://github.com/cli/cli/blob/0cf1092493af067646fc5f3db9421c6a6ec9c938/pkg/cmd/attestation/verification/sigstore.go). Signer-workflow matching is a prefix check, so the adapter uses exact certificate identity plus signer digest and rechecks the returned signed certificate fields.
- [sigstore-go v1.3.0 certificate extensions](https://github.com/sigstore/sigstore-go/blob/22d3691c7b8e0c5530fae3c05577690bfef5cd00/pkg/fulcio/certificate/extensions.go) and [verification result](https://github.com/sigstore/sigstore-go/blob/22d3691c7b8e0c5530fae3c05577690bfef5cd00/pkg/verify/signed_entity.go).
- [Fulcio GitHub principal](https://github.com/sigstore/fulcio/blob/78da569beb478103bf24d8b5085dd33f8ac33c7e/pkg/identity/github/principal.go) binds `runInvocationURI` to repository, run ID and attempt from GitHub OIDC claims.
- [Pinned attestation action](https://github.com/actions/attest-build-provenance/blob/4d101475d8b20a2381f78447822ac1eab6504dd8/action.yml) accepts a fixed subject name and digest and returns its bundle path.

The JSON is an array; certificate claims are flattened under `verificationResult.signature.certificate`, not a nested `extensions` field. The adapter requires exact issuer, SAN, signer URI/digest, GitHub-hosted environment, source repository URI/ID/digest/ref/private visibility, manual trigger, caller workflow URI/digest, and run invocation URI. It also checks the verified statement's sole subject name and SHA-256 digest. Workflow-controlled predicate fields cannot replace certificate claims.

A real offline verification using the pinned CLI and upstream CLI reusable-workflow artifact, signed bundle and upstream trusted-root fixture confirmed this output shape. That public upstream signature proves the CLI/schema mapping only; it does not prove a Knitli qualification run. The focused suite additionally executes the actual pinned verifier against an unsigned bundle and requires refusal. All positive host pipeline tests use an explicitly labelled trusted verifier stub.

## Remaining activation gates

The synthetic fixture creates its own temporary Git repository and drives the real snapshot/producer publication path with a deterministic completion stub. Acquisition must still yield `unavailable`, `missing-review-step`, `unverified`, and `unknown`; synthetic completion is never SDK completion.

Before a source/seal dispatch: independently review the actual workflow and host entrypoint, install the separately reviewed private caller pinned to the approved reusable SHA, and verify its invalid placeholder secret wiring. Before any full trust-channel or SDK claim: qualify an explicit host-owned Linux CLI/root pin, authenticated artifact download and bounded extraction, and separate acquisition after the entire source attempt completes successfully. Bind the caller and reusable revisions to trusted acquisition policy, verify a genuine private GitHub-only attestation, and prove rerun/sibling refusal. The local macOS verifier path is not a hosted verifier. Source/seal artifacts alone do not satisfy these remaining gates. No credential acquisition, native attachment, full Node process/Docker/UDS isolation claim, Mesh delivery, idle-session wake, or production activation is part of this slice.
